# 校园活动管理系统 V2.0

## 1. 项目简介

校园活动管理系统用于支持学校活动的发布、查看和报名管理。

V1.0 面向学生和活动组织教师两类用户，完成了「教师发布活动 → 学生查看活动 → 学生报名 → 教师查看报名学生」的核心业务闭环。

V2.0 在 V1.0 基础上引入**报名双状态模型**与**FIFO 候补队列**，并新增系统管理员角色。核心变化来自用户访谈：

- 学生无法判断自己是「已确认」还是「候补」，状态不透明；
- 热门活动满员后直接被拒绝，没有排队等待的途径；
- 学生临时不能参加时无法自行取消，教师名单无法及时更新。

## 2. 用户角色

### 学生

注册、登录、浏览活动、报名或进入候补、取消报名、退出候补、查看自己的报名状态与候补位置。

### 活动组织教师

登录、发布活动、修改活动、关闭活动，查看本活动的**已确认名单**与**候补名单**。

### 系统管理员（V2.0 新增）

登录，查看全平台活动列表与用户账号状态。**不提供**报名审批、候补处理、活动编辑等业务操作入口。

## 3. 功能范围

### V1.0 已实现

- 学生注册、登录
- 教师发布、修改、关闭活动
- 学生查看活动列表与详情
- 学生报名（防重、满员、过期校验）
- 教师查看自己活动的报名学生
- 基于角色的访问控制

### V2.0 新增

- `Registration` 引入 `status`（confirmed / waiting / cancelled）与 `queue_order`
- 满员后报名转入候补队列，不再直接拒绝
- 候补队列按 FIFO 排序，学生可查看自己的候补位置
- 已确认学生取消报名后，候补队列首位自动递补，剩余候补顺序前移
- 候补学生可主动退出候补
- 教师端报名管理页分「已确认名单」「候补名单」两个区域
- 新增 `admin` 角色与 `/admin/activities`、`/admin/users` 页面

### 明确不做

- 活动签到
- 评论留言、图片上传
- 短信 / 微信消息通知
- 第三方登录
- 管理员调整角色或停用账号

## 4. 核心业务流程

### 学生报名

1. 学生登录后进入活动详情页。
2. 系统按顺序校验：活动是否存在 → 是否已关闭 → 是否已结束 → 是否已报名。
3. 已确认人数未达上限：报名成功，状态 `confirmed`。
4. 已确认人数已达上限：进入候补队列，状态 `waiting`，`queue_order` 为当前候补人数 + 1。

### 学生取消 / 教师查看

1. 已确认学生取消报名，记录状态变为 `cancelled`，名额释放。
2. 系统取出该活动 `queue_order` 最小的候补记录，改为 `confirmed`，并重排剩余候补顺序。
3. 教师在报名管理页分别查看已确认名单与候补名单。

## 5. 重要业务规则

1. 一个学生对一个活动只有一条报名记录（`UNIQUE (student_id, activity_id)`）。
2. 已确认或候补中的学生不能重复报名同一活动。
3. 活动人数达到上限后不再新增已确认记录。
4. 已结束或已关闭的活动不能报名。
5. 候补递补严格按 `queue_order` 先到先得。
6. 只有已确认的报名可以取消；候补学生只能退出候补。
7. 教师只能管理自己发布的活动。
8. 管理员只能查看，不能处理报名业务。

## 6. 本地运行

```bash
pip install -r requirements.txt
python app.py
```

默认访问 `http://127.0.0.1:5000`。首次启动会自动建库并创建两个测试账号：

| 账号 | 密码 | 角色 |
| --- | --- | --- |
| teacher | teacher123 | 活动组织教师 |
| admin | admin123 | 系统管理员 |

学生账号通过 `/register` 页面自行注册。

## 7. 数据库升级说明

V1.0 的 `Registration.status` 只有 `active` / `cancelled` 两个取值。V2.0 启动时 `init_db()` 会检测 `queue_order` 字段是否存在，若不存在则执行一次表重建迁移：

- 新建 `Registration_v2` 表（三态 `status` + `queue_order`）；
- 把原表数据搬入，`active` 映射为 `confirmed`；
- 删除旧表并重命名。

迁移在同一个事务中完成，不需要手工删库。
