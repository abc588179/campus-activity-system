# 校园活动管理系统 V1.0 软件设计

## 1. 总体设计

### 1.1 设计目标

本设计服务于校园活动管理系统 V1.0，重点保证以下核心业务流程能够完整运行：

> 教师发布活动 → 学生查看活动 → 学生报名 → 教师查看报名学生

设计遵循简单、易运行和易维护的原则，不引入微服务、复杂中间件或复杂部署架构。

### 1.2 系统结构

V1.0 采用简单的单体应用结构，主要由以下部分组成：

1. **用户界面**：为学生和教师提供登录、活动查看、活动管理和报名操作入口。
2. **业务处理层**：根据当前登录用户的角色执行注册、登录、活动管理和报名规则校验。
3. **数据访问层**：负责读写用户、活动和报名记录。
4. **关系型数据库**：保存系统运行所需的用户、活动和报名数据。

系统协作方式如下：

- 用户界面接收学生或教师的操作请求。
- 业务处理层验证登录状态、用户角色和业务规则。
- 数据访问层读取或修改关系型数据库中的数据。
- 业务处理层将处理结果返回给用户界面。

所有功能放在一个应用中运行，适合课程实验和单人开发。V1.0 不设计独立的管理员端、消息系统、推荐系统或其他扩展服务。

## 2. 系统模块

### 2.1 用户认证模块

**负责内容：**

- 学生注册。
- 学生登录。
- 教师登录。
- 保存当前登录用户的身份和角色。
- 为后续操作提供学生或教师角色判断。

**与其他模块的关系：**

用户认证模块为学生活动模块、学生报名模块和教师活动管理模块提供登录状态和角色信息。其他模块在执行操作前，需要先确认用户已登录并具有对应角色。

### 2.2 学生活动模块

**负责内容：**

- 向已登录学生展示活动列表。
- 展示活动详情。
- 展示活动人数上限、当前报名人数和活动结束状态等报名判断所需信息。

**与其他模块的关系：**

学生活动模块读取 Activity 数据，并为学生报名模块提供活动标识和活动状态。学生从活动详情进入报名操作后，由学生报名模块继续处理。

### 2.3 学生报名模块

**负责内容：**

- 学生报名活动。
- 校验学生是否已经报名同一活动。
- 校验活动报名人数是否达到上限。
- 校验活动是否已经结束或关闭。
- 查看当前学生的报名记录。
- 取消当前学生的报名。

**与其他模块的关系：**

学生报名模块同时使用 User、Activity 和 Registration 数据。它依赖用户认证模块提供学生身份，依赖学生活动模块提供活动信息，并向教师活动管理模块提供报名学生数据。

### 2.4 教师活动管理模块

**负责内容：**

- 教师发布活动。
- 教师查看自己发布的活动。
- 教师修改自己发布的活动。
- 教师关闭自己发布的活动。
- 教师查看自己发布的活动的报名学生。

**与其他模块的关系：**

教师活动管理模块依赖用户认证模块确认当前用户是教师，并通过 Activity 的发布教师标识限制管理范围。查看报名学生时，模块通过 Registration 关联查询学生和活动数据。

## 3. 核心业务流程

### 3.1 教师发布活动

1. 教师登录系统。
2. 系统确认当前用户角色为活动组织教师。
3. 教师提交活动信息、活动结束信息和人数上限。
4. 系统保存 Activity，并记录当前教师为该活动的发布教师。
5. 活动进入可查看状态，学生可以在活动列表中看到并查看详情。

学生用户提交发布活动操作时，业务处理层应拒绝该操作。

### 3.2 学生查看活动

1. 学生登录系统。
2. 系统确认当前用户角色为学生。
3. 学生活动模块读取活动列表。
4. 学生选择活动后查看活动详情，包括活动信息、人数上限、当前报名人数和活动结束状态。

### 3.3 学生报名活动

1. 学生登录并打开活动详情。
2. 学生提交报名请求。
3. 系统确认当前用户是学生。
4. 系统检查该学生是否已有同一活动的有效报名记录。
5. 系统检查活动是否已关闭、是否已结束，以及当前有效报名人数是否达到人数上限。
6. 所有检查通过后，系统创建一条有效的 Registration 记录。
7. 如果任一检查不通过，系统拒绝报名并返回对应的失败结果，不创建新的有效报名记录。

### 3.4 教师查看报名学生

1. 教师登录系统。
2. 教师打开自己发布的活动。
3. 系统确认该活动的发布教师就是当前教师。
4. 系统通过 Registration 查询该活动的有效报名记录，并关联对应的学生 User 数据。
5. 系统向教师展示报名学生。

教师尝试查看其他教师活动的报名学生时，系统应拒绝操作。

### 3.5 关键规则处理

- **重复报名**：创建 Registration 前检查同一 `student_id` 和 `activity_id` 是否存在有效报名记录；存在时拒绝报名。数据库同时对这两个字段建立唯一约束，避免重复数据。
- **人数达到上限**：创建报名记录前统计活动的有效报名人数，并与 Activity 的人数上限比较；达到或超过上限时拒绝新的报名。
- **活动已结束**：将当前时间与 Activity 的结束时间比较，当前时间达到或超过结束时间时拒绝报名。
- **活动已关闭**：教师关闭活动后，Activity 状态变为已关闭；已关闭活动不能继续报名。
- **角色权限**：每次需要身份的操作都先验证登录用户角色。学生只能执行学生功能，教师才能发布和管理活动。
- **教师管理范围**：修改、关闭活动或查看报名学生前，检查 Activity 的发布教师是否为当前教师。

## 4. 数据设计

V1.0 只设计 User、Activity 和 Registration 三个核心数据表，使用关系型数据库保存数据。

### 4.1 User 用户表

| 字段 | 用途 |
| --- | --- |
| `id` | 用户主键，唯一标识用户 |
| `username` | 登录账号，用于识别用户 |
| `password` | 登录凭证信息；实际实现时应保存安全处理后的密码，不保存明文密码 |
| `role` | 用户角色，只允许 `student` 或 `teacher` |

**主键：** `id`。

**关键关系：**

- 一个教师可以关联多个 Activity。
- 一个学生可以关联多条 Registration。

**数据约束：**

- `id` 必须唯一。
- `username` 必须唯一且不能为空。
- `password` 不能为空。
- `role` 必须是学生或活动组织教师之一。

### 4.2 Activity 活动表

| 字段 | 用途 |
| --- | --- |
| `id` | 活动主键，唯一标识活动 |
| `title` | 活动名称 |
| `description` | 活动详细说明 |
| `organizer_id` | 发布教师的用户标识，关联 User.id |
| `max_participants` | 活动人数上限 |
| `end_time` | 活动报名截止和活动结束判断时间 |
| `status` | 活动状态，至少区分进行中和已关闭 |

**主键：** `id`。

**关键关系：**

- `organizer_id` 外键关联 `User.id`，且对应用户必须是教师。
- 一个教师可以发布多个活动。
- 一个 Activity 可以关联多条 Registration。

**数据约束：**

- `title`、`organizer_id`、`max_participants`、`end_time` 和 `status` 不能为空。
- `max_participants` 必须为正数。
- `organizer_id` 对应的用户角色必须是教师。
- `status` 只能使用系统定义的活动状态。

### 4.3 Registration 报名表

| 字段 | 用途 |
| --- | --- |
| `id` | 报名记录主键，唯一标识报名记录 |
| `student_id` | 报名学生的用户标识，关联 User.id |
| `activity_id` | 被报名活动的标识，关联 Activity.id |
| `status` | 报名状态，至少区分有效和已取消 |
| `registered_at` | 记录报名创建时间 |

**主键：** `id`。

**关键关系：**

- `student_id` 外键关联 `User.id`，且对应用户必须是学生。
- `activity_id` 外键关联 `Activity.id`。
- 一个学生可以报名多个活动。
- 一个活动可以有多个报名学生。
- 学生和活动通过 Registration 建立多对多关系。

**数据约束：**

- `student_id`、`activity_id`、`status` 和 `registered_at` 不能为空。
- `student_id` 对应的用户角色必须是学生。
- `status` 只能使用有效或已取消等系统定义状态。
- 同一个 `student_id` 和 `activity_id` 组合只能存在一条报名关系，防止重复报名。
- 活动的有效报名记录数量不能超过 `Activity.max_participants`。

## 5. 数据关系

### 5.1 教师与活动

一个教师可以发布多个活动，Activity 通过 `organizer_id` 记录发布教师。教师管理活动时，只能操作 `organizer_id` 等于当前教师用户标识的活动。

### 5.2 活动与报名学生

一个活动可以有多个报名学生。系统通过 Registration 的 `activity_id` 找到活动对应的报名记录，再通过 `student_id` 找到学生用户。

### 5.3 学生与活动

一个学生可以报名多个活动，一个活动也可以有多个报名学生。因此学生与活动是多对多关系，Registration 是两者之间的关联表。

### 5.4 防止重复报名

学生提交报名时，业务处理层先检查 `(student_id, activity_id)` 是否已经存在报名记录；数据表再通过 `(student_id, activity_id)` 的唯一约束防止并发或重复写入。取消报名只将原记录标记为已取消，不创建第二条记录；V1.0 不额外设计重复报名后的重新报名流程。

## 6. 权限设计

### 6.1 学生权限

学生登录后可以：

- 查看活动列表。
- 查看活动详情。
- 报名符合条件的活动。
- 查看自己的报名记录。
- 取消自己的报名。

学生不能：

- 发布活动。
- 修改或关闭活动。
- 查看教师活动的管理信息或其他学生的报名记录。

### 6.2 活动组织教师权限

教师登录后可以：

- 发布活动。
- 查看自己发布的活动。
- 修改自己发布的活动。
- 关闭自己发布的活动。
- 查看自己发布活动的报名学生。

教师不能：

- 以教师身份管理其他教师发布的活动。
- 修改或取消其他学生的报名记录。

### 6.3 权限检查原则

每个需要身份的操作都按以下顺序检查：

1. 确认用户已经登录。
2. 确认用户角色符合操作要求。
3. 如果操作针对具体活动，确认活动属于当前教师或学生拥有对应的报名记录。
4. 通过检查后才执行数据读取或修改。

## 7. 关键设计决策

### 7.1 身份与权限

**决策内容：** 在 User 表中使用 `role` 区分学生和活动组织教师，并在每次需要身份的操作前进行登录状态和角色检查。

**为什么这样设计：** V1.0 只有学生和教师两类角色，使用一个用户表和一个角色字段即可满足需求，结构简单，也能防止学生执行教师操作或教师越权管理活动。

### 7.2 重复报名规则

**决策内容：** 以 `(student_id, activity_id)` 作为报名关系的唯一组合，并在业务检查和数据约束两层防止重复报名。

**为什么这样设计：** 学生与活动之间的关系天然由这两个标识确定。业务检查可以给出明确的报名结果，数据约束可以避免重复数据进入数据库。

### 7.3 活动人数限制

**决策内容：** Activity 保存人数上限，报名时只统计有效 Registration 记录；有效报名人数达到上限时拒绝新的报名。

**为什么这样设计：** 人数上限是当前版本的核心业务规则。只统计有效报名可以使取消报名后的名额能够被重新计算，同时不需要增加额外数据表。

### 7.4 活动状态与报名条件

**决策内容：** Activity 使用 `status` 表示教师主动关闭的状态，并使用 `end_time` 判断活动是否已结束。只有活动未关闭、未结束且未达到人数上限时才允许报名。

**为什么这样设计：** “关闭活动”和“到达结束时间”都是当前需求中明确的报名限制，但产生原因不同。分别保存状态和结束时间，便于系统进行清晰、可测试的报名条件判断。
