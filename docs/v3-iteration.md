# 校园活动管理系统 V3.0 迭代说明

本轮依据教师提供的**模拟运行数据**（24 个活动、2878 条报名请求、1416 个会话、112 条匿名反馈）决定改进方向，不预设功能清单。

## 1. 数据分析结论

分析脚本见 `tools/analyze_data.py`，原始输出见 `docs/v3-analysis-output.txt`。

### 1.1 报名需求高度集中在「开放瞬间」

| 类型 | 活动数 | 开放 → 满额耗时 |
| --- | --- | --- |
| 爆款活动（A001 / A005 / A010 / A015 / A021） | 5（20.8%） | 4.3 – 5.2 分钟 |
| 其余活动 | 19（79.2%） | 20.5 – 36.0 小时 |

这 5 个活动在满额后分别涌入 132 / 146 / 139 / 143 / 141 条候补，合计 701 条，占全部候补的 80.0%。

### 1.2 峰值窗口内处理耗时显著升高

| 窗口 | 请求数 | p50 | p90 | 耗时 > 1300ms 占比 |
| --- | --- | --- | --- | --- |
| 开放后 0–20 分钟 | 1154（40.1%） | 729 ms | 1605 ms | 24.0% |
| 开放 20 分钟后 | 1724（59.9%） | 215 ms | 332 ms | 0.0% |

**控制结果类型后差异仍然存在**（排除「候补请求本身就慢」这一构成影响）：

| 结果类型 | 0–20 分钟 p50 | 20 分钟后 p50 | 倍数 |
| --- | --- | --- | --- |
| 已确认 accepted | 254 ms | 202 ms | ×1.26 |
| 转入候补 waitlisted | 1151 ms | 274 ms | ×4.20 |
| 重复提交 duplicate | 434 ms | 150 ms | ×2.89 |

结论：变慢的主要不是「所有请求」，而是「满员 / 候补」这条分支。

### 1.3 失败与重复提交相对富集于峰值窗口

全部请求中落在 [0, 20] 分钟区间的比例为 40.1%，以此为基准：

| 结果 | 落在峰值窗口的比例 | 富集倍数 |
| --- | --- | --- |
| 名额冲突 409 | 78.0% | ×1.95 |
| 重复提交 duplicate | 59.5% | ×1.48 |
| 服务端错误 500 | 43.8% | ×1.09 |
| 已确认 accepted | 32.5% | ×0.81 |

服务端错误的富集倍数接近 1，且样本仅 16 条，**不能据此认为峰值压力导致 500 错误**。

### 1.4 数据边界

- 数据是模拟材料，不是本组 V2.0 真实产生的日志，不能当作 V3.0 的实测结果；
- `user_behavior` 存在 28 条重复 `event_id`；
- `feedback` 只有 26 种原文、112 条记录，只能做定性归类，不能推断总体比例；
- `waitlisted` 与 `accepted` 的耗时差异既有分支差异，也可能包含排队因素，未做进一步归因。

## 2. 本轮决定的改进

| 编号 | 改动 | 依据 |
| --- | --- | --- |
| V3-R1 | Activity 增加 `confirmed_count` / `waiting_count` 冗余计数，报名不再在写锁内做 `COUNT(*)` 聚合 | 1.2 峰值分支变慢 |
| V3-R2 | 报名改用带条件的 `UPDATE` 原子占位（`WHERE confirmed_count < max_participants`） | 1.3 名额冲突与检查-使用间隙 |
| V3-R3 | 启用 WAL + `synchronous=NORMAL` + `busy_timeout=15000` | 1.2 峰值期提交耗时 |
| V3-R4 | 报名提交引入 `request_token` 幂等；同一令牌重放返回首次结果 | 1.3 重复提交 |
| V3-R5 | 报名表单按钮防抖 | 112 条反馈中 19 条提到「重复点击 / 不知道是否成功」 |
| V3-R6 | 为 `Registration(activity_id, status)` 与 `Registration(student_id)` 建索引 | 1.2 聚合与查询 |

本轮**不做**：候补结果通知（需外部通道）、活动检索筛选（与本次复现链路无关）、数据库迁移到 PostgreSQL（超出课程范围）。

## 3. 验证方式

- 功能回归：`python -m unittest discover -s tests -v`，共 27 项，覆盖 V1.0 原有规则、V2.0 候补规则与 V3.0 幂等/计数一致性；
- 并发压测：`python tools/loadtest.py`，同一脚本分别对 V2.0（tag `v2.0`）与 V3.0 运行 3 轮，每轮 60 名学生、容量 10、同时提交。

结果见实验三实验报告与 `docs/v3-loadtest-result.json`。
